# my-funds 开发与服务器管理架构

## 1. 目标

建立一套长期稳定的工作方式：Codex 在本地开发源码，GitHub 管理版本，服务器承载前端、后端、数据库和真实数据，所有远程操作通过 SSH 受控执行。

## 1.1 当前过渡期规则

服务器当前运行工作区是本阶段的代码行为基线。服务器存在未提交改动时，先在服务器端备份，再同步到本地审查；本地整理或新功能不得直接覆盖这些改动。审查通过后，将完整结果提交到 GitHub，后续发布以明确提交 SHA 为准。

## 2. 权威来源与职责

| 层级 | 位置 | 保存内容 | 不保存内容 |
| --- | --- | --- | --- |
| 本地开发 | `E:\myfund11111` | 源码、文档、虚构测试数据、运维脚本 | 真实数据库、`.env`、私钥、服务器备份 |
| 代码版本 | GitHub `ddkillerdd/my-funds` | 已提交源码、配置模板、迁移脚本 | 密钥、真实数据、运行日志 |
| 服务器运行 | 由 ops/.env 登记的服务器项目目录 | 前后端运行环境、MySQL、真实数据、上传文件、.env、备份 | 本地临时开发产物 |
| 用户访问 | 服务器域名 | 前端页面与 API 响应 | 本地开发服务 |

## 3. 数据流

```text
Codex 本地开发
    │
    ├── 静态检查 / 虚构数据测试
    │
    └── Git 提交与推送
             │
             ▼
          GitHub
             │
             └── SSH 部署指定提交
                      │
                      ▼
        服务器前端 + FastAPI + MySQL
                      │
                      ▼
                 浏览器访问
```

真实数据不进入本地开发链路。需要排查数据问题时，在服务器执行 SQL 或分析脚本，只返回聚合、脱敏和最小化结果。

## 4. 发布流水线

一次标准发布包含以下关卡：

1. 本地运行 ops/Invoke-LocalChecks.ps1，检查工作区、语法、测试和前端构建。
2. 提交并推送明确的 Git SHA。
3. SSH 只读预检服务器磁盘、服务和仓库状态。
4. 在服务器创建数据库与配置备份。
5. 服务器拉取并部署指定 SHA。
6. 必要时执行数据库迁移。
7. 检查后端健康接口、前端页面、容器或服务状态。
8. 验证失败时回滚到上一已知正常 SHA，并恢复兼容的数据库状态。

## 5. 权限模型

- SSH 使用独立部署用户，优先密钥认证，不在仓库保存密码。
- 日常巡检使用只读命令，不读取 `.env` 或输出数据库明细。
- MySQL 建议区分应用账户、只读巡检账户和迁移账户。
- 高风险操作遵循最小权限、先备份、可回滚和逐项确认原则。

## 6. 环境规划

- `production`：服务器真实前端、后端和数据库。
- `staging`：建议后续在同一服务器或独立服务器建立，使用脱敏或虚构数据验证发布。
- `local`：只做源码开发、静态检查、合成 MySQL、API 集成测试和前端构建，不保存真实数据。

本地后端固定使用 Python 3.12.13，MySQL 合成库通过 `fund-advisor/docker-compose.local.yml` 绑定到 `127.0.0.1:3307`。完整初始化和使用方法见 `docs/development/LOCAL_DEVELOPMENT_ENVIRONMENT.md`。

如果暂时没有 staging，数据库结构变化和大版本发布必须安排维护窗口，并在服务器保留可验证的备份。
