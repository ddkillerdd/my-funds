# Codex 与 OpenClaw 协同规范

> 生效日期：2026-09-02
> 适用范围：`my-funds` 本地开发、GitHub 协同、服务器紧急热修、staging 和生产发布
> 当前状态：协同规则已固化；backend unit 的失败自动重试已经按授权停止，未修改 OpenClaw、cron、unit 文件或生产工作区

## 1. 目的

本项目从“OpenClaw 直接管理服务器工作区”过渡到“本地开发、GitHub 固化、明确 SHA 发布”。本规范用于防止 Codex 与 OpenClaw 同时修改同一文件、覆盖未提交热修、重复拉取或重启服务。

## 2. 权威来源

| 对象 | 权威来源 | 说明 |
| --- | --- | --- |
| 正常开发与发布代码 | GitHub 上已审查的明确提交 SHA | 不使用本地或服务器脏工作区作为发布包 |
| 当前生产行为 | 服务器只读巡检结果 | 用于确认正在运行的版本、服务和未提交热修 |
| 真实业务数据 | 生产数据库 | 不复制到本地或 staging |
| 密钥与运行配置 | 服务器本地受控配置 | 不进入 Git、文档、聊天或测试输出 |
| staging 数据 | 独立合成数据库与仓库测试夹具 | 不连接生产数据库 |

服务器状态可以说明“生产当前如何运行”，但不能替代 Git 提交。GitHub 提交可以作为发布源，但不能证明服务器已经部署到该提交。

## 3. 当前协同基线

- 本地与 GitHub 发布候选：`codex/p0-server-readiness` 的 `5f8bc18683c807dd0ef18b3b35735a7b4cffd016`。
- 服务器生产工作区：`main` 的 `afc19e9b203141e8e604fc3f1b9f5dd438637a81` 加 3 个未提交热修文件。
- 本地另有 5 个第四组既有改动，不属于当前 staging 或生产发布范围。
- OpenClaw 相关进程仍存在；当前未观察到持续写入，但没有证据表明其已退出生产控制。
- backend unit 配置仍为 `Restart=always`，但已停止失败自动重试；旧健康 uvicorn 仍属于 `tat_agent.service`。前端继续由 systemd 管理。
- 生产数据库备份与恢复证据尚未满足，生产发布保持阻塞。

每次开工都必须重新核对该基线。发现漂移时，以实时只读结果为准并停止写操作。

## 4. 职责边界

### 4.1 Codex 或 Luna

- 在本地仓库完成审查、开发、回归测试、文档和 Git 固化。
- 使用 `codex/<任务>` 分支，提交前保护用户已有改动。
- 只从明确 Git SHA 设计或部署 staging。
- 未经确认，不修改服务器生产工作区、服务、数据库或 OpenClaw 配置。

### 4.2 OpenClaw

- 在过渡期承担生产状态观察和用户明确授权的紧急操作。
- 开发时使用 `openclaw/<日期>-<任务>` 分支，不直接在 `main` 长期保留唯一热修副本。
- 紧急服务器改动必须记录基础 SHA、文件、原因、验证结果和回收状态。
- 不自动覆盖 GitHub 指定发布 SHA，不在 Codex 已认领文件上并发写入。

### 4.3 用户

- 确认任务负责人、生产维护窗口和有状态操作。
- 分别授权备份、部署 staging、服务重启、数据库变更和生产切换。
- 对 OpenClaw 与 Codex 的冲突范围作最终取舍。

## 5. 开工登记

每个任务开始前记录以下信息：

```text
执行端：Codex / Luna / OpenClaw
任务：
基础分支：
基础 SHA：
允许修改文件：
禁止修改文件：
是否操作服务器：否 / 只读 / 待确认写入
是否操作服务或数据库：否 / 待确认
另一执行端状态：空闲 / 只读 / 执行中 / 未确认
```

“未确认”视为存在冲突风险，不得开始同文件写入或生产发布。

## 6. 分支与文件所有权

- Codex/Luna 使用 `codex/<任务>`；OpenClaw 使用 `openclaw/<日期>-<任务>`。
- `main` 只接收已经审查、测试并具备回滚证据的提交。
- 同一任务范围内，一个文件同一时间只能有一个写入负责人。
- 另一执行端需要修改已认领文件时，先由当前负责人提交并交接，再通过 merge 或 cherry-pick 继续。
- 禁止使用 `git reset --hard`、强制推送、覆盖式同步和脏工作区直接拉取来解决冲突。
- 来源不明的服务器差异必须先只读审查；不能逐块解释时停止，不猜测保留顺序。

## 7. 服务器紧急热修回收流程

1. 记录生产当前 SHA、服务状态和目标文件。
2. 确认 Codex/Luna 没有同时修改这些文件。
3. 只修改故障所需最小范围，不混入策略参数或其他清理。
4. 使用虚构数据或最小安全检查验证，不输出秘密和真实持仓。
5. 将热修整理到 `openclaw/<日期>-<任务>` 或本地审查分支。
6. 运行对应测试，提交并推送到 GitHub。
7. 记录热修是否已进入发布 SHA，以及服务器脏文件何时安全回收。

如果紧急程度迫使服务器先改后提交，服务器差异只能作为临时事实来源；故障稳定后必须优先完成回收，期间暂停同文件的本地开发。

## 8. 发布窗口中的 OpenClaw 与服务控制

发布前必须只读确认：

- OpenClaw 是否有本项目任务、子进程或持续写入。
- cron、systemd timer、守护进程或容器是否会拉取、覆盖、回滚或重启。
- 后端与前端的实际父进程、工作目录、启动命令和重启策略。
- OpenClaw 任务与 systemd `Restart=always` 是否为相互独立的控制链。

暂停 OpenClaw 自动任务或修改 systemd、cron 前，必须列出目标、当前值、拟修改值、恢复方式和维护窗口，并单独获得确认。不能仅凭进程名直接终止任务，也不能把停止 OpenClaw 等同于停止应用服务。

发布后先验证 Git SHA、服务健康、关键 API 和日志，再按记录恢复自动化。恢复后再次确认没有回写旧版本。

## 9. staging 隔离规则

- staging 位于 OpenClaw 生产工作区之外，从 GitHub 检出明确 SHA。
- 使用独立 Python 环境或经审查的镜像，不复用生产虚拟环境。
- 使用独立 MySQL 8.0.43 合成数据库、独立卷和随机本地凭据。
- 后端、前端和数据库只绑定 `127.0.0.1`，用户通过 SSH 隧道访问。
- 调度器、启动净值回补、邮件外发和自动任务保持关闭。
- 不修改生产 systemd、防火墙、域名、反向代理和 OpenClaw 恢复规则。
- staging 进程名、目录、端口和停止方式必须明确，不能被生产自动化误识别。

staging 部署需要服务器写操作确认；staging 验收通过也不自动授权生产切换。

## 11. Sol 与 Luna 多任务调度

- 用户默认只在 Sol 指挥任务中提出目标和授权。
- Sol 负责规划、风险审查、后台发送单阶段执行包、等待结果和验收；Luna 是经授权阶段的唯一执行端。
- 默认不切换用户窗口。Sol 与 Luna 对话上下文彼此隔离，但共享本地工作区、GitHub 和服务器状态。
- Luna 执行期间，Sol 保持只读；OpenClaw 不得同时修改 Luna 已认领的生产对象。
- Git 提交、GitHub 推送、staging 写入、服务操作、数据库操作和生产切换分别设置授权门。
- 完整状态机、执行包、结果格式和重启恢复规则见 `CODEX_LUNA_ORCHESTRATION.md`。

## 12. 立即停止条件

出现任一情况，停止所有写操作并报告：

- OpenClaw 或另一执行端正在修改同一文件。
- 自动拉取、覆盖、回滚或重启机制的触发条件无法确认。
- 本地、GitHub 或服务器的分支、SHA、脏文件与交接基线不一致。
- 需要读取或输出秘密、真实持仓或完整生产日志才能继续。
- staging 可能连接生产数据库、使用生产外发凭据或暴露公网端口。
- 发布需要覆盖生产脏工作区、复用生产依赖或跳过备份门禁。
- 服务异常扩大、健康检查失败或无法说明恢复路径。
