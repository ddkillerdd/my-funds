## 测试结果

## 发现的额外问题

### Bug 4: 实际分析延迟远超预估值

**预估**: Step1 每只 3s + 1.6s 间隔 = 20s 完成 4 只
**实际**: 第 1 只超时 120s，第 2/3 只 ~75s，第 4 只 >90s 仍在跑

**根因分析**:
之前的单次测试（3.4s）是在无其他请求的情况下测的。
生产环境中 NewAPI 可能有其他请求排队。
_step-3.7-flash 偶发超长延迟_ 导致 4 只基金的计算时间远超预估。

**修复方案**:
- 降低超时: 120s → 45s（超过 45s 直接降级更实用）
- 预估值更新: 每只基金 10-30s，4 只 + 诊断 = 50-120s

### Bug 5: 报告生成时间太长，curl 等不了

**现象**: curl --max-time 300 不够用
**修复**: 不修（这是 curl 调用的问题，生产环境是浏览器发起 AJAX，没有 300s 超时限制）

### Bug 6: 部分调用成功但返回 JSON 不标准

**现象**: 第二测试中第 2/3 只 LLM 返回 HTTP 200 OK，但无 "WARNING Parse" 日志（说明正常解析）
第 1 只超时降级

**待验证**: 第 4 只结果

### Bug 7: LLM JSON 返回字段名不一致 (导致 Step2 KeyError)

**现象**: 第二次测试中，Step1 `_parse_json()` 解析成功，但 LLM 返回的 JSON 缺少 `health_score` 字段
**根因**: LLM (step-3.7-flash) 的 JSON 输出不稳定，有时用了不同字段名或遗漏字段
**修复**: 在 Step1 解析后统一标准化 → 缺失字段补齐默认值
